Follow-up: the referral save mutation accepts an optional expected config version for compatibility and rejects a mismatched version before writes; the updated editor supplies it. The card editor now participates in the existing Web unsaved-change registration. The referral client and mutation must be deployed together; no deployment has been performed. Existing clients that omit the version are not protected by this new comparison. The rendered editor, concurrent-device workflow and full form coverage have not yet been verified. Initial scan found 74 `.collect()` occurrences across the eight requested backend files; occurrences require individual assessment and are not all necessarily unbounded or safe to replace.

Further follow-up: the Web editor is separated from the unchanged Native route. Save is visibly disabled while a version/business conflict is unresolved, including the race where the server rejects a write before the subscription refresh arrives. Two simulated editing sessions verify accepted and rejected writes, including a legacy client. An older client can still overwrite a newer client because the version argument remains optional; eliminating that risk requires an explicit compatibility/rollout decision, not a claim of complete protection.

The card-management list and detail now use the existing business-and-createdAt event index for the same 30-day range and reuse a single membership result. In an in-memory indexed test with 1,000 old events, two relevant recent events and another business, each query selected two events and preserved active/total member and event metrics. This is a simulated read count, not a measured Convex latency. The remaining source scan finds 72 `.collect()` occurrences (business 15, campaigns 7, customerCards 3, customerLifecycle 2, dashboard 5, events 1, loyaltyPrograms 7, referrals 32); each needs individual semantic and scale review. No arbitrary data caps were introduced.

The machine-readable `STAGE2_COLLECT_INVENTORY.json` records each remaining occurrence and its query expression; `scripts/audit-stage2-collect.mjs` regenerates it. It is an inventory, not evidence that all occurrences have been reviewed or optimized. Notably the admin referral search still performs global full-table reads. Customer history, dashboard lifetime metrics, quotas and reward logic must not be capped without an equivalent design and tests.

The conflict save button is disabled consistently with its accessibility state, including a server rejection that arrives before the subscription update; the user can explicitly discard the draft only when the authoritative current version is available. A regression test simulates two editing sessions and a legacy write. This does not prove rendering, network races on actual devices or old-client prevention of overwrites. The Native editor was subsequently updated at the user's explicit request to send a version and preserve a dirty draft; unrelated Native routes remain protected by the existing regression test.

Latest follow-up: navigation guards are now registered per form; one clean or unmounted form cannot remove another form's dirty guard. A rendered React test verifies that navigation and PWA unsaved state remain active until both forms are clean. This does not cover every application editor or a real installed PWA. When a referral status is supplied, the customer-referral list now scopes the existing index by both business and status without changing the existing result sorting or limits. Admin audit lookup now uses the existing target index when both type and target ID are supplied; admin authorization and fallback behavior are retained. Local mocked tests verify filters, sorting and denied admin access. No actual server read or latency benchmark was performed.

The Web card-creation wizard now registers a dirty draft with the shared guard and prevents route removal until the user confirms discard; this includes non-default appearance selections. Focused local tests cover wizard validation and a rendered shared-guard interaction, but do not establish physical browser, business switching, save-race or PWA acceptance for the complete wizard. The remaining input-bearing surfaces require individual assessment: a text search or OTP input is not automatically a persistent editing form, and blindly guarding all 38 files containing input elements would change behavior.

Correct replacement requires a separately designed indexed search or explicit pagination contract across all five record types, with authorization and ordering tests; none was deployed or silently truncated. The unfiltered `adminListReferralAuditLog` fallback also remains unbounded; its exact target lookup has already been narrowed using the existing index. Other inventory entries remain pending individual semantic/scale review.
